# San Francisco Vendor Payments: Accounts Payable Controls Review

Testing a real city's payment records for duplicate payments and duplicate vendor records, using Python, SQL (DuckDB) and Excel.

## The problem

Large organizations pay thousands of suppliers through hundreds of thousands of transactions a year. When accounts payable controls are weak, the same bill gets paid twice, one supplier ends up in the vendor list under two names, and money leaves without anyone noticing. These are some of the most common and most preventable AP failures.

San Francisco publishes every vendor payment it makes. This project uses one full fiscal year of that data to answer a practical question an internal auditor or controller would ask: **are there payments that look like duplicates, and which ones should someone review first?**

## Data

| | |
|---|---|
| Source | DataSF, [Vendor Payments (Vouchers)](https://data.sf.gov/City-Management-and-Ethics/Vendor-Payments-Vouchers-/n9pm-xkyq), published by the SF Controller's Office |
| Period | Fiscal year 2026 (July 1, 2025 to June 30, 2026) |
| Size | 511,226 rows, $16.84 billion paid, about 6,500 vendor names |
| In scope | 350,716 supplier payments, $6.10 billion (services, supplies, equipment and construction) |

About 64% of the dollars the city paid were not supplier purchases (payroll tax remittances, debt service, employee benefits, grants, refunds), so they were excluded from testing. The full breakdown is in `outputs/scope_summary.csv`.

## Approach

1. **Prepare.** Combine rows split across funds into one row per payment, and check the total still ties to the cent ($16,842,902,152.64 in and out).
2. **Scope.** Label every payment as in scope or out, with a reason. Nothing is deleted.
3. **Duplicate payment test.** Flag two different payments to the same vendor for the exact same amount close together. HIGH risk if on the same PO within 30 days, MEDIUM if any PO within 14 days.
4. **Refine.** Separate flags with an innocent explanation (a matching reversal, monthly fees, multi-unit equipment orders, repeat supply orders) from the ones that need a person to look. Score what is left and build a top-25 review list. Then check the "recurring" payments themselves for months where a monthly bill was paid more than once, since a recurring label would otherwise hide exactly that kind of duplicate.
5. **Duplicate vendor test.** Use fuzzy name matching to find suppliers that may exist twice under different names, then check whether the same amount was paid to both names.
6. **Review.** Assess the top flags and vendor candidates. Assessments live in `review_notes/` as CSV files, so they are versioned and flow into the workpaper automatically.
7. **Workpaper.** Collect everything into an Excel audit workpaper with review columns, and write a results summary.

Full detail, including every threshold and why it was chosen: [`docs/methodology.md`](docs/methodology.md)

## Results

Headline numbers are generated by the pipeline in [`docs/results_summary.md`](docs/results_summary.md). Findings and recommendations for a non-technical reader are in [`docs/audit_memo.md`](docs/audit_memo.md), which fills its numbers in from the results on every run, so the memo can never drift from the data.

**Key results (FY2026):**

- $16.84B paid in total. $6.10B was supplier spending in scope, and 133,800 payments ($6.04B) were tested.
- The first pass flagged 31,126 payment pairs. After refinement, 1,520 payments ($23.3M, 0.39% of the amount tested) remained unexplained.
- Of the 25 highest-priority cases, 18 ($3.78M) were recommended for inquiry and 7 ($0.95M) looked legitimate on review. The top case is two identical $219,589 payments on the same date with no purchase order.
- 295 monthly bills were paid more times than the months they cover, 365 extra payments worth up to $6.6M. This is an upper bound, since catch-up for the previous fiscal year looks the same.
- The largest duplicate vendor record: ComputerLand of Silicon Valley, with 1,016 payments ($15.6M) under one record and 98 ($1.7M) under another.

**What changed along the way.** The first pass produced over 31,000 flags, most of them recurring payments or already reversed. Each round of review exposed a pattern the rules had missed, in both directions. Monthly rent paid several months at once looked like overpayment until each bill was compared with the months it covers. Numbered housing partnerships looked like duplicate vendors until the matcher learned Roman numerals. And an "installment" rule was deliberately left out, because on a two-payment order it would hide exactly the double payments the test exists to find. That judgment is most of the work in this project.

## What this does not prove

The public data has no invoice numbers, only approximate dates, and no vendor IDs or addresses. So a flag here is a lead for inquiry, not a confirmed duplicate. Some flags will turn out to be legitimate, and the workpaper is set up to record that. One recommendation from this work is that publishing invoice numbers would make public oversight of city spending far more precise.

## How to run

Requires Python 3.10 or later.

```bash
git clone <this repo>
cd sf-ap-controls
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python run_pipeline.py
```

The first run downloads about 511,000 rows from DataSF, which takes a few minutes. Later runs reuse the downloaded data. Use `python run_pipeline.py --refresh` to download a fresh copy, or `--from 4` to rerun from a given step.

All settings (scope, thresholds, time windows) are in `src/config.py`.

Python handles downloading, fuzzy matching and orchestration. Every data rule and test is written in SQL, so the logic can be read and checked without reading Python. Excel is used only for review and presentation.
